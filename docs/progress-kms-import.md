## Lessons learned

Carry-forward knowledge that changes how later phases are built: scope changes, workarounds, and decisions that constrain future work. This is not a status log — phase completion is tracked by the checkboxes above. Append entries only when they will affect a future phase.

- **CI trigger scope:** CI runs only on pushes to `main` and on `pull_request`. Pushes to other branches (e.g. the `claude/*` feature branches) do not trigger CI — open a PR to exercise CI for branch work.
- **Wrapping is RFC 5649, not RFC 3394 (Phase 3):** KMS `RSA_AES_KEY_WRAP_SHA_256` wraps the key material with *AES Key Wrap with Padding* (RFC 5649, OpenSSL `id-aes256-wrap-pad`, AIV `0xA65959A6`), **not** plain RFC 3394. The wire format submitted to `ImportKeyMaterial` is `RSA-OAEP-SHA256(AES key) || RFC5649-wrap(key material)` — RSA part first. The crypto is verified by RFC 5649 known-answer tests in `pkg/kmsimport/wrap_test.go`; do not change the concat order or padding without re-checking the KATs.
- **Library API (Phase 3):** `pkg/kmsimport.Import(ctx, opts...) (Result, error)` with options `WithClient`, `WithKeyID`, `WithKeyMaterial` (PKCS#8 DER). Sentinel errors `ErrNoClient`/`ErrNoKeyID`/`ErrNoKeyMaterial` are returned for missing inputs before any AWS call. `Result.KeyState` is inferred as `"Enabled"` on success because the two-method `KMSClient` interface (locked) cannot call `DescribeKey`. Phase 4 CLI must build the SDK client and inject it via `WithClient`.
- **PEM decode is a library concern (corrected Phase 4):** the library exposes `KeyMaterialFromPEM(pemBytes) ([]byte, error)` (PEM → PKCS#8 DER). Decoding the operator's key file is part of pushing a key, so it lives in `pkg/kmsimport`, **not** the CLI. An earlier draft put this in `pkg/cli` (`decodeKeyMaterial`); that was wrong and has been moved. The CLI only reads the file and calls the library. Format requirements R2/R3/R4/R6 are satisfied by this function.
- **Outstanding manual smoke (Phase 3):** the real-KMS import acceptance criterion (import a throwaway RSA-2048 key into an EXTERNAL-origin KMS key, confirm `Enabled`) could **not** be run in the sandbox (no AWS credentials/network policy). The wire format is covered by KATs + a round-trip unit test, but the live import remains an operational check to perform before relying on the tool in production. **Phase 4 inherits this:** the binary's end-to-end run against a real KMS key is likewise unverified in the sandbox — same operational smoke covers both.
- **CLI seam (Phase 4):** the testable boundary in `pkg/cli` is `runImport(ctx, out io.Writer, client kmsimport.KMSClient, keyID string, pemBytes []byte)` — it calls the library's `kmsimport.KeyMaterialFromPEM` to decode, `kmsimport.Import` to push, and writes the confirmation. `Command()`'s Action does only flag parsing, `os.ReadFile`, and SDK client construction (`config.LoadDefaultConfig` → `kms.NewFromConfig`) above it. Later phases extend, not replace: Phase 6 adds the `--key-arn`/`--alias` target flags + `--profile`/`--region` (route into `LoadDefaultConfig`), Phase 8's `--json` must route output through `runImport` (the single Fprintf is the only stdout write today).
- **Expiry wiring (Phase 7):** `--expires` validation (RFC 3339 parse + past-date rejection) lives in the CLI as `parseExpiry`, called in `Command()`'s Action **before** `LoadDefaultConfig`/any AWS call (R18). The library gained a `WithExpiry(time.Time)` option that flips the IKM input to `KEY_MATERIAL_EXPIRES` + `ValidTo` (R17); `runImport` now takes a `time.Time` expiry (zero value = non-expiring) and only appends `WithExpiry` when non-zero, so the Phase 3 default-no-expiry path (R16) is untouched. **R19 (reimport, no mode switch) needed no code** — the same `Import` invocation already serves initial import and reimport; only AWS enforces the same-material constraint, so it remains part of the deferred real-KMS smoke.
- **JSON output + error handling (Phase 8):** `--json` is a `BoolFlag` whose value threads into `runImport(..., jsonOut bool)`; when set, `runImport` marshals an `importResult{KeyID, Alias (omitempty), KeyState}` (JSON keys `keyId`/`alias`/`keyState`) and writes only that, suppressing the human-readable line (R26). **R27 needed no new code** — AWS failures already propagate as Go errors from `Import` → `runImport` → the Action → `cmd.Run`, and `cmd/kms-import/main.go` prints them to stderr + `os.Exit(1)`; urfave/cli v3's default `ExitErrHandler` does not print plain (non-`ExitCoder`) errors, so nothing leaks to stdout. `runImport` returns the import error *before* any write, so quiet/JSON-mode stdout stays empty on failure (`TestRunImport_FailureWritesNothing`). The JSON field names are the documented shape; Phase 10 docs must match `keyId`/`alias`/`keyState`.
- **PEM format coverage (Phase 5):** `KeyMaterialFromPEM` now switches on the `pem.Decode` block `Type` — `"RSA PRIVATE KEY"` (PKCS#1, converted to PKCS#8 DER), `"PRIVATE KEY"` (PKCS#8, returned as-is after a parse check), and any other header → error naming the unsupported format (R3, R4). **R5 needed no new code:** Phase 4's `fmt.Errorf("read key file: %w", err)` already names the file and reason (the wrapped `*os.PathError` carries both); Phase 5 only added a regression test (`TestCommand_UnreadableKeyFile`). Format detection keys solely off `block.Type`; there is no format flag.
